# P3 Advanced authorization and scale: task specs

These 12 tasks add conditions, sharing, partner tenants, impersonation, migration, metering and performance. They end at gate **G3 Feature complete** (week 20) with all 28 cases green.

## X-01 ABAC conditions and request context

**Lane** L5 · **Depends on** Z-03 · **Estimate** 4 d

**Goal:** permissions can carry conditions evaluated at check time (C23).

**Scope:** catalog declares which conditions a permission supports (`amount_limit`, `ip_range`, `working_hours` with tenant time zone); assignment API accepts condition parameters; translator writes conditional tuples; SDK context resolvers (from body, route, headers, client IP); missing context → deny with reason `missing_context`.

**Acceptance criteria:** conditions validated at assignment time; decisions logged with context hash, never raw values that may be personal data.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-X01-01 | I | Approver with `max_amount` 10,000 approves 9,999 / 10,001 | allowed / denied |
| TC-X01-02 | I | Check without `amount` in context | denied ( `missing_context` ) |
| TC-X01-03 | I | `ip_range` 10.0.0.0/8, request from 192.168.1.5 | denied |
| TC-X01-04 | I | `working_hours` 09:00–17:00 Africa/Cairo at 18:00 Cairo | denied |

## X-02 Resource sharing and business resource template

**Lane** L5 + L4 · **Depends on** Z-01 · **Estimate** 5 d

**Goal:** apps register their own resource types and share resources across nodes or with users (C17).

**Scope:** resource type registration (owner node relation, shareable roles) generating model fragments like `invoice` in section 5.3; sharing API (share with user, group, node; NodeOnly or with descendants; revoke); `ResourceOwnerChanged` event from apps through SDK helper; list resources shared with me.

**Acceptance criteria:** sharing never grants more than the sharer holds; revoking a share removes access within 2 s.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-X02-01 | I | Invoice owned by Cairo, shared to Dubai node | Dubai approvers can approve it; others in UAE cannot (unless inherited) |
| TC-X02-02 | I | Share invoice with Omar as viewer | Omar can view, not approve |
| TC-X02-03 | I | Sharer without `invoices_share` | Rejected |
| TC-X02-04 | I | Revoke share | Access gone < 2 s |

## X-03 Tenant hierarchy and partner grants

**Lane** L1 + L4 · **Depends on** T-01, A-03 · **Estimate** 5 d

**Goal:** resellers manage customer tenants with explicit, time-bound grants (C22, UC-14).

**Scope:** parent tenant link; partner creates child tenant; `TenantGrant` (grantee tenant, role, scope node, expiry) created or approved by customer owner; partner users act in the customer tenant through tenant switch with `tid` = customer and claim `ptid` (partner tenant); expiry job; customer can revoke; audit shows partner identity.

**Acceptance criteria:** parent tenant has no implicit access; grants are visible only to the granting customer and the grantee partner.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-X03-01 | I | Partner admin without grant opens customer tenant | Denied |
| TC-X03-02 | I | Grant Admin at root for 30 days | Partner admin can manage; token has `ptid` |
| TC-X03-03 | I | Grant expires (test clock) | Access removed, sessions in customer tenant revoked |
| TC-X03-04 | I | Second partner lists grants | Cannot see first partner's grant |

## X-04 Impersonation

**Lane** L3 · **Depends on** P-03, G-01 · **Estimate** 4 d

**Goal:** support staff can act as a user safely and visibly (C20, UC-13).

**Scope:** impersonation request (target, reason, duration ≤ 60 min); optional tenant-owner approval per tenant policy; token exchange in impersonation mode issuing `act`; PDP impersonation policy denying sensitive permissions (catalog flag `sensitive`); banner in portals; user notified after session; full audit.

**Acceptance criteria:** owners cannot be impersonated for sensitive actions; impersonated actions always show both identities in audit.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-X04-01 | I | Support impersonates Mona with reason | Token `sub` =Mona, `act.sub` =support |
| TC-X04-02 | I | Impersonated session calls `roles_assign` (sensitive) | denied |
| TC-X04-03 | I | Tenant requires approval; owner rejects | No token issued |
| TC-X04-04 | I | Audit entry for an impersonated action | actor = Mona, impersonator = support |

## X-07 GDPR export and erasure

**Lane** L2 + all · **Depends on** module events · **Estimate** 5 d

**Goal:** users and tenants can exercise data rights.

**Scope:** export job collecting data from every module through a `IPersonalDataProvider` contract (JSON bundle, download link valid 24 h); erasure: user deleted, memberships removed, audit entries pseudonymized (actor ID kept as hash), PDP tuples removed; tenant export on offboarding (UC-15).

**Acceptance criteria:** every module implements the contract (architecture test); erasure leaves no email or name in any table except legal-hold records.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-X07-01 | I | Omar requests export | Bundle includes Acme and Globex memberships, sessions, credentials metadata |
| TC-X07-02 | I | Omar deletes account | No rows with his email; audit pseudonymized; tuples gone |
| TC-X07-03 | U | New module without `IPersonalDataProvider` | Architecture test fails |

## X-09 Performance and scale testing

**Lane** L10 + L11 · **Depends on** Z-03 · **Estimate** 5 d

**Goal:** prove the non-functional targets in section 3.4.

**Scope:** k6 scenarios: login burst (500/s), token refresh, PDP mixed checks (5,000/s), admin writes with propagation measurement; datasets of 10,000 tenants and 5 million users (synthetic); tuning of connection pools, caches, OpenFGA concurrency and PostgreSQL indexes; capacity report.

**Acceptance criteria:** all NFR latency and throughput targets met on the reference environment; report with bottlenecks and sizing.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-X09-01 | P | 500 logins/s for 10 min | p95 token endpoint < 150 ms, error rate < 0.1% |
| TC-X09-02 | P | 5,000 PDP checks/s | p95 < 20 ms cached, < 50 ms uncached |
| TC-X09-03 | P | 200 admin writes/s | Propagation p99 < 2 s |
| TC-X09-04 | P | Kill one PDP pod under load | No failed checks beyond retry budget |

## G-15 User import with password hash migration

**Lane** L2 · **Depends on** I-01, A-01 · **Estimate** 5 d

**Goal:** customers move from a legacy system without forcing password resets.

**Scope:** bulk import API and CSV/JSON (users, memberships, node, roles); supported hashes: bcrypt, PBKDF2 (configurable), scrypt, Argon2; hash stored with algorithm tag and upgraded to platform hash on next successful login; lazy migration option (verify against legacy endpoint on first login, then store); dry run and report.

**Acceptance criteria:** imported users sign in with their old password; hashes upgraded on first login; 100,000 users import in < 10 min.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-G15-01 | I | Import user with bcrypt hash, sign in with original password | Success; stored hash now platform format |
| TC-G15-02 | I | Unsupported hash type in file | Row rejected in dry run |
| TC-G15-03 | I | Lazy migration: legacy endpoint confirms password | User created locally; legacy not called again |
| TC-G15-04 | P | 100,000 users | < 10 min |

## G-26 Usage metering

**Lane** L7 · **Depends on** U-01 · **Estimate** 4 d

**Goal:** accurate usage per tenant for plans and billing.

**Scope:** counters: monthly active users (unique `sub` per tenant per month), M2M tokens issued, PDP checks, SSO connections, SCIM operations; aggregated hourly into `metering.usage`; API and admin view; export for billing systems; soft limits with warnings, hard limits per plan (BR-14).

**Acceptance criteria:** MAU counts exact (deduplicated); metering failure never blocks login.

**Test cases**

| ID | Level | Scenario | Expected |
|---|---|---|---|
| TC-G26-01 | I | Omar logs in 10 times to Acme in one month | Acme MAU +1 |
| TC-G26-02 | I | Omar logs in to Acme and Globex | Each tenant counts him once |
| TC-G26-03 | I | Metering store down during login | Login succeeds; events buffered and replayed |
